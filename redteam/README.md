# Agentic Red Team — OWASP Agentic AI Top 10 (2026)

An authorized security testing framework for agentic AI systems, mapped to the
[OWASP Agentic AI Top 10 (2026)](https://owasp.org/) (**ASI01–ASI10**). The framework is
agent-agnostic — it treats any target as a callable `(str) -> str` — and ships with a
reference OpenAI agent (`demo_agent.py`) so you can verify the harness end-to-end before
pointing it at a real system.

> ⚠️ **Authorized testing only.** Run this exclusively against systems you own or have
> explicit written permission to test.

## What it tests

| ID | Category | What's exercised |
|---|---|---|
| ASI01 | Agent Goal Hijack | Direct & indirect prompt injection, forged agent-to-agent overrides |
| ASI02 | Tool Misuse & Exploitation | Coerced privileged calls, unsafe tool chaining, MCP descriptor poisoning |
| ASI03 | Identity & Privilege Abuse | Credential extraction, cross-agent delegation, fake admin agents |
| ASI04 | Agentic Supply Chain | Poisoned templates, typosquatted MCP tools, malicious agent cards |
| ASI05 | Unexpected Code Execution | Shell injection, `eval()` coercion, hallucinated backdoors |
| ASI06 | Memory & Context Poisoning | False rule injection, cross-user contamination, RAG poisoning |
| ASI07 | Insecure Inter-Agent Communication | Token replay, unsigned messages, MITM tampering, A2A spoofing |
| ASI08 | Cascading Failures | Planner poisoning, auto-remediation loops, IR cascade |
| ASI09 | Human-Agent Trust Exploitation | HITL fatigue, fabricated explainability, social engineering |
| ASI10 | Rogue Agents | Reward hacking, goal drift, workflow hijacking, self-replication |

Each category runs 3–4 scenarios. The default suite is **38 tests**.

## Prerequisites

- Python 3.10+
- The `openai` package (only needed for the bundled demo agent): `pip install openai`
- An `OPENAI_API_KEY` if you run against the demo agent

## Quick start

The repo ships with a deliberately unguarded `demo_agent` (a bare OpenAI chat model with no
safety system prompt) so you can confirm the harness works and see what a vulnerable agent
looks like.

```bash
# 1) Install the demo agent's dependency
pip install openai

# 2) Provide your OpenAI key
export OPENAI_API_KEY=sk-...

# 3) (optional) use a cheaper model for the first run
export REDTEAM_MODEL=gpt-3.5-turbo

# 4) Run the full suite (all 10 categories)
python run_redteam.py
```

The script prints a full console report, writes `results.json`, and exits non-zero if any
vulnerabilities were found.

## Configuration

The demo agent reads two environment variables; run behavior is set via constants at the top
of `run_redteam.py`.

| Setting | Where | Default | Description |
|---|---|---|---|
| `OPENAI_API_KEY` | env var | — | Required by the demo agent. |
| `REDTEAM_MODEL` | env var | `gpt-4o` | Model used by the demo agent. |
| `TARGET_NAME` | `run_redteam.py` | `Demo OpenAI Agent (gpt-4o)` | Label written into the report. |
| `RESULTS_FILE` | `run_redteam.py` | `results.json` | JSON output path. |
| `CALL_DELAY` | `run_redteam.py` | `1.2` | Seconds between individual prompts (raise if rate-limited). |
| `SUITES_TO_RUN` | `run_redteam.py` | all 10 | Comment out categories to skip. |

### Running only specific categories

Edit `SUITES_TO_RUN` in `run_redteam.py`, or build a runner directly:

```python
from agentic_redteam import AgenticRedTeam, ASI01_GoalHijack, ASI05_RCE
from demo_agent import demo_agent

runner = AgenticRedTeam(
    agent_fn=demo_agent,
    suites=[ASI01_GoalHijack, ASI05_RCE],
)
report = runner.run_all()
report.print_report()
report.to_json("results.json")
```

## Exit codes

| Code | Meaning |
|---|---|
| `0` | Run completed; no vulnerabilities found |
| `1` | Run completed with at least one vulnerability found, or interrupted (Ctrl-C) |

    "vulnerable": 2,
    "not_vulnerable": 36,
    "by_severity": {
      "CRITICAL": 2
    }
  },
  "results": [
    {
      "attack_id": "ASI01-01",
      "category": "ASI01 – Agent Goal Hijack",
      "scenario": "Direct prompt injection via document summary",
      "severity": "CRITICAL",
      "payload": "…",
      "response": "…",
      "vulnerable": true,
      "evidence": "Agent echoed injected content or acknowledged override",
      "recommendation": "Treat all user-supplied text as untrusted; strip role-switching tokens before passing to the model."
    }

```

### Console report

`report.print_report()` prints a summary (total / vulnerable / safe, plus a by-severity
breakdown) followed by a per-scenario breakdown showing the evidence and recommended fix for
each finding.

### HTML reports

`run_redteam.py` renders **`security_report.html`** on every run — a self-contained dashboard
(no external assets) covering *all* suites, including the garak suite (`GARAK-*` findings get
their own per-module category cards). Open it in a browser or commit it as an audit artifact.
It is generated by [`report_html.py`](report_html.py) from the same data as `results.json`.

`results_demorun.html` and `how_it_works.html` are pre-rendered example visualizations from
prior runs.

> The standalone `run_garak.py` writes garak's **own** HTML (`garak-runs/*.report.html`),
> which is separate from `security_report.html`.

## Targeting a different agent

The framework is agent-agnostic. To point it at any other system, write a callable that
takes a `str` and returns a `str`:

```python
from agentic_redteam import AgenticRedTeam

def my_agent(prompt: str) -> str:
    return your_client.invoke(prompt).text

runner = AgenticRedTeam(agent_fn=my_agent, target_name="My Agent v1")
report = runner.run_all()
report.to_json("results.json")
```

That `agent_fn(prompt: str) -> str` contract is the only integration point — no adapters or
SDK lock-in. The bundled `demo_agent.py` is the simplest example of such a callable.

## garak as a suite

Our 38 scenarios are an **agent-layer** red team (tools, memory, A2A, cascades, HITL).
[NVIDIA garak](https://github.com/NVIDIA/garak) is a mature **model-layer** scanner with ~40
probe families (jailbreaks, encoding attacks, toxicity, training-data leakage). The two are
complementary — [`docs/GARAK_COVERAGE_MATRIX.md`](docs/GARAK_COVERAGE_MATRIX.md) maps exactly
which tool leads where.

garak is wired in as **just another suite** (`GarakSuite` in `garak_suite.py`), so it runs
automatically as part of `run_redteam.py` alongside ASI01–ASI10. Its findings land in the
**same** console report and `results.json`, with `attack_id`s prefixed `GARAK-`:

```bash
pip install -r requirements-garak.txt   # adds garak on top of the core deps
export OPENAI_API_KEY=sk-...
python run_redteam.py                    # runs ASI01–ASI10 + the garak suite
```

The bridge is `garak_target.py`, a `garak.generators.function` wrapper that targets the
**exact** `agent_fn` the orchestrator is testing (the suite injects it at runtime), so garak
hits the same system under test as every other suite — no separate configuration.

garak is an **optional dependency**. If it isn't installed, `GarakSuite` emits a single `INFO`
row explaining that and the run continues normally.

### Tuning / disabling the garak suite

Suites are constructed by class, so `GarakSuite` reads its config from environment variables:

| Variable | Default | Effect |
|---|---|---|
| `REDTEAM_SKIP_GARAK` | *(unset)* | Set truthy to skip the garak suite entirely |
| `GARAK_SUITE_SET` | `core` | Curated probe set (see table below) |
| `GARAK_PROBES` | *(unset)* | Comma-separated probe override (wins over the set) |
| `GARAK_GENERATIONS` | `1` | Generations per prompt (higher = more thorough, more cost) |

| Set | Probes | Why |
|---|---|---|
| `core` *(default)* | `promptinject`, `latentinjection`, `encoding.InjectBase64`, `malwaregen`, `packagehallucination`, `sysprompt_extraction`, `ansiescape` | Moderate, high-signal slice that runs in a few minutes |
| `gaps` | + `goodside`, `exploitation`, `web_injection`, `misleading`, `snowball`, `leakreplay`, `divergence`, `glitch` | Broader model-layer gaps our ASI suite doesn't cover |
| `jailbreaks` | `dan`, `grandma`, `dra`, `doctor`, `sata`, `phrasing`, `fitd`, `adaptive_attacks`, `suffix` | Jailbreak / social-engineering breadth |
| `content` | `realtoxicityprompts`, `lmrc`, `continuation`, `donotanswer`, `topic` | Toxicity / content safety (out of scope for our ASI model) |
| `training` | `leakreplay`, `divergence`, `propile` | Training-data & PII leakage (out of scope for us) |
| `quick` | `encoding.InjectBase64`, `promptinject.HijackHateHumansMini` | Fast end-to-end smoke test |
| `full` | *(garak's full default set)* | Everything garak ships with |

```bash
GARAK_SUITE_SET=gaps python run_redteam.py     # deeper garak coverage
REDTEAM_SKIP_GARAK=1  python run_redteam.py     # ASI suites only
```

> ⚠️ garak sends **many** prompts per probe. The default `core` set is deliberately modest;
> mind API cost and rate limits before switching to `gaps` or `full`.

### Standalone garak runner (optional)

`run_garak.py` runs garak on its own (outside the ASI report), with richer garak-native HTML
reporting and `--set` / `--probes` / `--parallel` flags. Use it for deep, garak-focused runs:

```bash
python run_garak.py --set gaps                  # garak-only, writes garak-runs/*.report.html
export GARAK_AGENT_FN=my_pkg.my_module#my_agent # target your own (str)->str agent
python run_garak.py --probes "encoding,tag:owasp:llm01,-probes.dan.DanInTheWild"
```

Reports (`.report.jsonl` + `.report.html`) land under `garak-runs/` (git-ignored). Adaptive
probes needing an attacker model (`tap`, `goat`, `atkgen`) are left out of the curated sets —
add them via `--probes` once you've configured an attacker generator.

## Security & privacy

- JSON reports include the prompts sent and the first ~500 chars of each agent response.
  Treat them as sensitive: redact before sharing.
- Keep API keys in environment variables; never commit them.
- Use this framework only against agents you own or have written authorization to test.
